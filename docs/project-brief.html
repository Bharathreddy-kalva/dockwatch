What hiring managers actually score

Across the portfolio checklists and job-market reports I read, the same six things keep appearing: a real problem with a business reason to exist, data that is messy and large enough to be uncomfortable, a modern and recognisable tool stack, clean modular code with tests, a README that explains the problem and the results in the first screen, and a pipeline that runs end to end on a schedule without a human clicking anything. The most common failure is the inverse of that list: a clean Kaggle CSV, a notebook, no automation, no deployment, no numbers.

The Qarera analysis of 360,000 postings adds two more signals worth designing around. Python plus SQL plus PostgreSQL plus Docker plus AWS is the intersection that appears in both backend and data-engineering listings, so a project built on exactly that stack is searchable by both kinds of recruiter. And "AI" is now the second most requested hard skill overall, so one small, well-scoped AI feature at the end of the project is worth more than it costs.

The design rule for this project: every component has to be justified by the problem, not by the resume. "I added Kafka because the feed updates every 30 seconds and I need replay" is a great interview answer. "I added Kafka to show Kafka" is not.

The flagship: Dockwatch

The problem. Bike-share operators (Citi Bike in New York, Divvy in Chicago, Bay Wheels in San Francisco) lose money every time a rider arrives at an empty dock or a full one. They pay crews to drive vans around moving bikes, a job called rebalancing. Deciding which stations will run empty in the next 30–60 minutes, and in what order to visit them, is a real operational question with real cost attached. That is the whole product: predict dock-outs before they happen, and hand the crew a ranked list.

Why this data. Every major bike-share system publishes a free, keyless, real-time feed in a standard called GBFS. station_status.json refreshes every 30–60 seconds with bikes and docks available at every station (New York alone has ~2,000 stations), and the specification requires it to be no more than five minutes stale. Separately, Citi Bike publishes monthly trip-history CSVs going back to 2013, with millions of rows per month, which gives you a large batch dataset for the warehouse side. Add Open-Meteo for weather (free, no key) because rain and temperature are the strongest predictors of demand. Three sources, zero API keys, zero cost, and a mix of live stream plus large historical batch. That mix is exactly what the checklists say they want to see.

What "done" looks like. A public URL where anyone can open a map, see every station coloured by predicted risk of running out in the next 30 minutes, hit an API for the rebalancing queue, and look at a Grafana dashboard showing request latency across three API replicas behind a load balancer while a load test is running. Plus a README with an architecture diagram and five measured numbers.

Architecture

The data model, briefly

Four core tables carry the whole thing. stations is a slowly changing dimension (stations move and get renamed; keep history with valid_from/valid_to). station_status_snapshots is the big one: one row per station per poll, about 2,000 × 2 per minute ≈ 5.8 million rows a day in New York, which is exactly the size where naive queries stop working and you get to demonstrate partitioning, BRIN indexes and EXPLAIN ANALYZE. trips holds the historical CSVs (tens of millions of rows after a few months). rebalance_tasks is the write side of the API, with an outbox table next to it so task creation and the Kafka event are committed in the same transaction.

-- The query that justifies the whole warehouse:
-- for each station, minutes until empty at the current drain rate
WITH recent AS (
  SELECT station_id, observed_at, bikes_available,
         bikes_available - LAG(bikes_available) OVER (
           PARTITION BY station_id ORDER BY observed_at) AS delta
  FROM station_status_snapshots
  WHERE observed_at > now() - interval '30 minutes'
)
SELECT station_id,
       LAST(bikes_available, observed_at)           AS bikes_now,
       SUM(delta) FILTER (WHERE delta < 0) / 30.0   AS drain_per_min,
       LAST(bikes_available, observed_at)
         / NULLIF(-SUM(delta) FILTER (WHERE delta < 0) / 30.0, 0) AS minutes_to_empty
FROM recent GROUP BY station_id
ORDER BY minutes_to_empty NULLS LAST LIMIT 50;

Window functions, filtered aggregates and a partition-pruned time range in one query. Interviewers ask about exactly these.

The hard parts, and why they're the point

Snapshot volume. Six million rows a day means that within a week the naive "index on observed_at" approach stops fitting in memory. The correct move is daily range partitions with a BRIN index on observed_at (the data is append-only and time-ordered, so BRIN costs almost nothing) and a retention job that detaches partitions older than 30 days into Parquet. Write down the query time before and after; that's the resume bullet.

The feed lies a little. GBFS last_reported timestamps go backwards, stations vanish and reappear, and some systems publish the same payload for minutes at a time. Your poller should diff against the previous payload and only publish changes, which also cuts Kafka volume by roughly 80%. Handling that is your data-quality story.

Exactly-once is a lie, dedupe is the truth. Kafka consumers will redeliver. Make the snapshot upsert keyed on (station_id, last_reported) so redelivery is harmless, and the rebalance-task consumer idempotent on the outbox event id. Be ready to explain in an interview why you chose at-least-once plus idempotency over transactional producers.

The load test has to hurt. Run k6 at, say, 500 requests per second against /stations/risk with the cache disabled first, watch Postgres saturate, then enable Redis and watch p95 drop from hundreds of milliseconds to single digits. Then kill one API replica during the run. The Grafana screenshot of that sequence is the single most persuasive image in the whole README.

Scope discipline. Pick one city (New York has the most stations and the best trip history). Do not add a second city, a mobile app, or user accounts until everything in the coverage table is green. Breadth across cities proves nothing; depth in one proves everything.

A six-week plan, part time

Each phase ends with something that runs and something written down. If a week slips, cut the AI bonus, never the load test.

Week 1

Skeleton and the live feed

Docker Compose with Postgres, Kafka, Redis. Poller for GBFS with diffing and backoff. Consumer writing partitioned snapshots. Alembic migrations. First Grafana panel: rows/min.

Ships: live data flowing for 7 days straight, schema diagram.
Week 2

Batch history and the warehouse

Airflow DAG for monthly trip CSVs → PySpark → Parquet (MinIO) → Postgres. dbt project with staging/intermediate/marts and tests. Open-Meteo hourly join.

Ships: 3+ months of trips loaded, dbt docs site, a page of EXPLAIN ANALYZE timings.
Week 3

The API

FastAPI: /stations, /stations/{id}/history (cursor pagination), /stations/risk, POST /rebalance-tasks with idempotency keys and the outbox. Redis cache and token-bucket rate limit. pytest with testcontainers.

Ships: OpenAPI docs, 80%+ test coverage, replay-safe POST.
Week 4

Load balancing, load testing, observability

Nginx in front of three replicas with health checks. Prometheus + OpenTelemetry across every hop. k6 scenarios: baseline, cache off vs on, kill-a-replica, rate-limit engage.

Ships: the Grafana screenshot, a load-test report with five numbers.
Week 5

Cloud and CI

Terraform: EC2 (Compose on it is fine), RDS Postgres, S3. GitHub Actions running pytest, dbt tests and a nightly smoke k6. Public URL for the map and the API.

Ships: live URL, green badge, Terraform in the repo.
Week 6

Prediction, README, write-up

Dock-out classifier (LightGBM on mart features: hour, weekday, weather, recent drain) or the text-to-SQL endpoint. README with diagram, numbers, "how to run in one command". A 1,000-word blog post on the hardest problem.

Ships: the thing you link on your resume.

How it reads on the resume

Write the bullets from the measurements, not the tool list. Fill in your real numbers; these are the shapes.

  • Built a real-time bike-share rebalancing platform ingesting ~5.8M station-status events/day from GBFS via Kafka into partitioned PostgreSQL; cut hot-path query time from 2.4 s to 38 ms with BRIN-indexed daily partitions and continuous aggregates.
  • Designed an Airflow + PySpark batch pipeline loading 40M+ historical trips into Parquet and Postgres, modelled with dbt (18 models, 61 tests) into marts powering a 30-minute dock-out predictor with 0.81 precision.
  • Served predictions through a load-balanced FastAPI tier (Nginx least-conn, 3 replicas) with Redis caching and a Lua token-bucket rate limiter; sustained 500 req/s at p95 < 20 ms and zero 5xx during a replica failure under k6.
  • Implemented the transactional outbox and idempotent consumers for at-least-once delivery; verified no data loss across a 2-minute broker outage in an automated chaos test.
  • Provisioned on AWS free tier with Terraform (EC2, RDS, S3); GitHub Actions CI runs pytest, dbt tests and nightly load tests; full OpenTelemetry tracing and Grafana dashboards.

Three alternatives, if bikes aren't your thing

Each of these has the same shape (a live stream, a big batch, a query-heavy store, a load-balanced API) and the same free, keyless data. Pick one you'd actually enjoy explaining for forty minutes.

Editstorm: edit-war detection on Wikipedia

source: Wikimedia EventStreams (SSE, recentchange) · ~30–60 events/s, 24/7

Consume the firehose of every edit across all Wikipedia languages, window it by article, and flag articles where reverts spike (an edit war) or where a brand-new account makes many rapid edits (likely vandalism). Batch side: the full monthly page-view dumps. Strengths: a true always-on stream with real volume, windowed aggregations in Spark Structured Streaming or Flink, and a clear "anomaly detection" story. Weakness: harder to describe the business value in one sentence.

Lookalike: phishing-domain watcher on certificate transparency

source: Certstream (WebSocket) · thousands of new certificates/minute

Every TLS certificate issued in the world gets logged publicly. Stream them, fuzzy-match new domain names against a list of brands (paypa1-login.com, amaz0n-secure.net), score them, and expose an alerting API. This has the highest raw throughput of the four, which makes the Kafka partitioning, consumer-group scaling and backpressure story real. Great fit if you want to lean toward security or platform roles. Weakness: dedupe and trigram matching in Postgres (pg_trgm, GIN indexes) get hard fast, which is either a bonus or a risk depending on your appetite.

Aftershock: global seismic monitoring with geospatial queries

source: USGS Earthquake API (REST) + EMSC (WebSocket) · plus 50 years of historical catalogue

Stream new quakes, store them in PostGIS, and serve "what shook within 100 km of this point in the last hour" plus per-region rate baselines to detect swarms. Batch side: the full USGS historical catalogue for baselines. Strengths: PostGIS spatial indexes (GiST) are a distinctive skill, the map is visually striking, and the alerting use-case is obviously useful. Weakness: event rate is bursty and low on quiet days, so your load test has to be synthetic.

What to avoid

Don't build it in a notebook; build it as a repo with a Makefile and a Compose file. Don't stop at "it works locally" when a free-tier deploy is a week of work. Don't list technologies you touched for an hour; list the ones you can defend under questioning, and be honest in the README about what's simplified (Compose on a single EC2 instead of Kubernetes is a perfectly good choice for a solo project, and saying so shows judgement). Don't skip the measurements: an interviewer who reads "p95 dropped from 340 ms to 12 ms after adding Redis" will ask you about it, and that conversation is the interview going well.

One last thing: put the README diagram and the five numbers above the fold. The hiring manager has five to ten minutes. Make the first screen do the work.
